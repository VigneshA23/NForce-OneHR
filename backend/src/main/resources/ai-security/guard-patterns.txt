# What ConfidentialityGuard refuses, one Java regex per line. Case-insensitive unless a pattern
# says otherwise with (?-i:...); ^ and $ match at line breaks.
#
# The real boundaries are structural: the model is never given secrets, other users' data or
# internal ids, and retrieval is filtered by role in SQL. These patterns make refusals consistent
# and deterministic on top of that. Every probe in src/test/resources/ai-eval/security-probes.txt
# must match, and every question under its "answer" heading and in ai-eval/questions.yaml must
# not - so tighten or loosen a line here only with that test running.
#
# Sections:
#   shared        - checked on the question and on the answer
#   question      - a question about the assistant or OneHR's internals -> "can't disclose"
#   manipulation  - an attempt to change its rules or the user's access -> "can't change that"
#   compact       - spelled-out letters ("s y s t e m p r o m p t"), matched with spaces removed
#   answer        - an answer that leaks internals -> replaced with "can't disclose"
#   answer-action - an answer claiming it did something; it is read-only -> "cannot make changes"
#   fragment      - "name = regex" pieces, written {name} in any pattern (or in a later fragment)
#   role          - "NAME = regex", the roles a user can claim; {role} stands for each in turn
#   role-claim    - the question claims a role the account does not hold -> "not assigned that role"
#   access-claim  - the question claims someone granted it more access -> "access comes from your roles"
#   answer-role   - the answer gives the user a role the account does not hold -> the same as role-claim
#   answer-access - the answer says the user was granted access -> the same as access-claim
# The role and access sections are checked against the roles the account really holds, so they
# have their own lists in security-probes.txt.
