1 · GAP‑036 — Policy hard-delete still has a real hole

Current
Four guards (current employee count, allocation count, penalty existence, "not the last policy") all pass for a policy that was the org's real governing policy for months purely via default-fallback — no explicit allocation was ever created, and no discrepancy during that window happened to reach APPLY_PENALTY. Its real, multi-version rule history is then permanently destroyed.
Recommended
Add a fifth guard: block hard-delete whenever the policy has more than one PenalizationPolicyVersion, or any version whose effectiveFrom is in the past — i.e. "this policy was ever actually live" — forcing deactivate-instead-of-delete for anything with real history. A brand-new, never-activated policy (one version, never past its effective date) stays deletable.
Alternative
Convert delete() into "deactivate if it has history, hard-delete only if it doesn't" — removing the separate toggle/delete UI distinction for used policies entirely.
Risk
The recommended option is the smaller behavior change (delete gets stricter, nothing gets easier), but it does mean an admin who wants to clean up a genuinely-dead old policy will be forced to leave it around inactive instead. The alternative removes an explicit user choice.
Needs your call
Which guard shape, and whether "any past-dated version" or "more than one version" is the right trigger.

2 · GAP‑033 — Regularization reversal is scoped too broadly

Current
reverseForApprovedRegularization reverses every still-active penalty for that employee+date, regardless of discrepancy type. A regularization that only corrects a late check-in will also reverse an unrelated, still-legitimate WORK_HOURS_SHORTAGE penalty from the same day.
Recommended
Scope reversal to only the discrepancy type(s) the regularization's corrected time window would actually change — which requires knowing, at approval time, which exception type(s) the correction addresses (full-day vs. check-in-only vs. check-out-only), and ideally re-deriving whether that discrepancy would still fire against the corrected attendance record before reversing it.
Alternative
Keep "reverse everything for the date" as the rule, but make it an explicit, documented business decision ("a regularization corrects the whole day's record, full stop") rather than an accidental byproduct of a date-only query — the code comment already asserts this is intentional, so this may be accepted behavior, not a bug.
Risk
The recommended fix requires building real re-evaluation logic (this doubles as the fix for GAP‑034/GAP‑035 below) — a materially larger change than anything else in this pass. The alternative leaves a scenario where an employee could have a legitimate shortage penalty erased as a side effect of an unrelated correction.
Needs your call
Is "reverse the whole day" actually the intended HRMS rule (in which case this is a documentation fix, not a code fix), or should reversal be scoped per discrepancy type (a real re-evaluation feature)?

3 · GAP‑034 — Leave approval never re-evaluates penalties

Current
Only regularization approval triggers penalty reversal. An approved half-day leave that retroactively lowers a day's expected work minutes below what the employee actually worked never touches an already-applied WORK_HOURS_SHORTAGE penalty for that date.
Recommended
Section 10's own example is the target behavior: leave approval should trigger the same kind of re-evaluation regularization approval does, scoped to WORK_HOURS_SHORTAGE/NO_ATTENDANCE (the two types whose "expected" side leave approval can change).
Alternative
Leave this out of scope for this pass and document it as a known limitation — HR can still manually cancel a stale penalty today via the existing cancel endpoint.
Risk
Recommended option touches LeaveService.approve(), a high-traffic, already-complex path, and needs the same re-evaluation machinery as GAP‑033. Manual cancellation as a stopgap is real today but relies on HR noticing.
Needs your call
In scope for this pass, or deferred as a documented limitation pending a shared re-evaluation engine?

4 · GAP‑001 — Inactive policy still fully governs

Current
Confirmed by the code's own javadoc: deactivating a policy only removes it from dropdowns; every resolution path (allocation, legacy FK, default) ignores status entirely.
Recommended
Your Section 5 model: historical resolution is untouched; a NEW evaluation for TODAY-or-later should not select an inactive policy unless explicitly allowed. Concretely: resolveAssignedOrDefaultPolicyId/resolveEffectiveVersion skip inactive policies when resolving for future/current dates, but historical `AttendancePenalty` rows already reference a specific `policyId`/`policyVersion` snapshot and are unaffected either way.
Alternative
Only block an INACTIVE policy from being the default fallback (oldest-created), but still honor it if an employee has an explicit allocation or legacy FK pointing at it — treating "inactive" as "retired from being anyone's fallback" rather than "can't govern anyone."
Risk
The recommended option changes behavior for any org that has an INACTIVE policy still explicitly allocated to real employees today — those employees would suddenly need a new policy resolved for them (falling through to legacy/default), which may or may not be desired. The alternative is safer but weaker.
Needs your call
Should INACTIVE block ALL forward resolution (allocation + legacy + default), or only block it from being selected as the org DEFAULT?

5 · GAP‑006 — Allocation-gap fallback strategy

Current
Hardcoded: any employee with no allocation and no legacy FK always resolves to the org's oldest-created policy, with zero way to configure otherwise, and zero dedicated report of "who's on the gap/default path."
Recommended
Your Section 4 naming: introduce an explicit, configurable DEFAULT_POLICY vs REQUIRE_ALLOCATION strategy (org-level setting). Keep DEFAULT_POLICY as the actual default so no existing org's behavior changes unless they opt in.
Alternative
Don't add a strategy toggle yet — just make the existing per-row resolvedPolicySource ("ALLOCATION"/"LEGACY"/"DEFAULT") filterable/reportable on the Allocation screen, so gaps are visible without changing resolution behavior at all.
Risk
A real REQUIRE_ALLOCATION mode means some employees would resolve to no policy at all — every attendance evaluation for them becomes a no-op until someone allocates them. That's a meaningful behavior cliff if an org flips the setting without allocating everyone first.
Needs your call
Build the configurable strategy now (bigger, but matches your ask directly), or ship only the visibility/reporting half this pass and defer the strategy toggle?

6 · GAP‑002/003/004/005 — Employee lifecycle vs. allocation

Current
There is no dedicated "terminate" action — only setActiveStatus(active=false) and softDeleteUser, both of which are also usable for reasons other than termination (the codebase doesn't distinguish "terminated" from "temporarily deactivated"). Neither touches allocations. Reactivation silently resumes any old open allocation.
Recommended
Your Section 6 model (close allocation on termination, explicit re-allocation on rehire) is right if deactivation always means termination in this HRMS. That needs verifying against how HR actually uses the deactivate/reactivate toggle today — closing a real employee's allocation because they were deactivated for an unrelated reason (e.g. a data-entry freeze, an investigation) would be a real regression.
Alternative
Do nothing to the deactivate/reactivate path itself; instead, surface "this reactivated employee has a pre-existing allocation from before deactivation" as a flagged item for HR to confirm/re-decide, rather than silently closing or silently resuming it.
Risk
Hooking allocation-closure into the generic deactivate toggle is the highest-blast-radius change in this whole list if deactivation is used more broadly than "termination" today.
Needs your call
Confirm whether setActiveStatus(false)/softDeleteUser are ONLY ever used for termination in this HRMS (I can verify frontend call sites if you want that checked before deciding), and whether you want auto-close-on-deactivate or a flagged-for-HR-review approach instead.

C · Business-rule register (this round's additions)

01
Reversal scope is per-date, not per-type. findByEmployeeUserIdAndIncidentDate + reverseForApprovedRegularization's loop reverse every still-active penalty for an employee+date regardless of discrepancyType, by explicit design comment — currently stated as intentional, flagged above as decision #2.
02
Leave approval never invalidates a penalty. The only automatic reversal trigger anywhere in the codebase is RegularizationService.approve()'s final-stage branch.
03
No penalty is ever recomputed against corrected data. Every reversal is a blind status flip; WorkHoursShortageCalculationService is never re-invoked after the fact to check whether a shortage genuinely still exists.
04
LEAVE_ATTENDANCE_CONFLICT is correctly, deliberately never gated by working-day status — verified unchanged from this session's earlier GAP‑007 work; a punch during approved leave is flagged even on a holiday/weekly-off.
05
Allocation-gap fallback always resolves to the org's oldest-created policy whenever at least one PenalisationPolicy row exists anywhere — there is no code path that leaves an employee with "no policy, no evaluation" today.
06
Policy status is read in exactly two places (the toggle itself, and the summary DTO) — no resolution or evaluation code checks it anywhere.
07
A penalty is only ever persisted on an APPLY_PENALTY engine decision — NO_MATCH/EXEMPT/CONFIGURATION_REQUIRED/BUFFER_PENDING all persist nothing, which is exactly why a policy can genuinely govern for months and still show zero AttendancePenalty references (the root cause of GAP‑036).

PayrollNoZero payroll fields, zero event/outbox mechanism exist. Adding new columns is cheap (no FK on AttendancePenalty by design), but the only existing concurrency guard (transitionStatus's conditional UPDATE) is scoped to the single status column and assumes it's the sole lifecycle indicator — a payroll-sync process would need its own idempotency mechanism built from scratch.
